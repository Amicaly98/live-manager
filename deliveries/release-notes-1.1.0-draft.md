## 本次更新要点

### 1. 稳定性（本次改动的重点）

- **停止优先**：开播过程中（选任务、等跨日重置、平台返回慢）执行“停止”，
  不会再被恢复成直播；迟到的旧停止请求也不会停掉后来开启的新直播。
- **控制票据**：每次操作携带一次性操作票据，过期重放会被明确拒绝并提示，
  不会悄悄执行成另一次操作。
- **重连与断网**：面板查询改为有限次重试，断网不再卡住界面；重连只针对
  确认已被平台关闭的直播，且手动分区 / FFmpeg 推流同样能恢复。
- **不再误杀外部程序**：删除了过去按名字结束 `ffmpeg.exe` 的做法，只回收
  本应用自己启动的进程；你另外开的 OBS 或 FFmpeg 不受影响。
- **退出更干净**：退出时会等旧的后端进程确认回收再拉起新的；正常退出后
  不会留下本应用的后端或 FFmpeg 进程（实测零残留）。

### 2. 数据目录统一（升级必读）

- 所有可写文件（任务库、状态、cookies、日志、分区缓存）统一放在
  `%APPDATA%\bilibili-live-manager\data\`。
- 从更早版本（1.0.0）升级时，首次启动会自动把**旧版本工作目录**（经快捷方式
  启动时就是安装目录）里散落的旧数据**带备份迁移**过来（备份在同目录
  `migration_backup\<时间戳>\`），**不会覆盖**新数据。
- **卸载不会删除这些数据**：卸载只清理程序与快捷方式，数据保留在上述
  目录里，重装后继续使用。

### 3. 重开应用不会自动开播

- 上次是“停止并退出”的话，重新打开应用**只会提示可以继续**，需要你自己
  确认后才恢复；不会一开机就自动开播。

### 4. 分区数据改为运行时刷新

- 安装包内只带一份**首次启动用的分区清单**（12 个大区 / 444 个子分区），
  首次启动复制到数据目录；**已有分区缓存不会被安装、升级或重装覆盖**。
- 之后分区有变化，请在应用内点“刷新分区”，**不需要重新下载安装包**。
- 分区数据不再作为程序文件随版本发布。

### 5. 其他

- 打包内置后端（`run.exe`），使用本应用**无需安装 Python**。
- 前端类型检查（`vue-tsc --noEmit`）与构建（`npm run build`）均通过；本机实际
  解析 `typescript 5.9.3` + `vue-tsc 2.2.12`，`frontend/package.json` 声明为
  `^5.3.0` / `^2.2.12`（**未钉死具体版本**）。
  （`typescript 5.3.3` + `vue-tsc 1.8.27` 的 exact 钉死是服务器前端仓库的做法，
  与本仓库无关。）

## 安装与升级

1. 运行 `直播控制系统 Setup 1.1.0.exe`，按向导选择安装目录即可。
   - **含中文的安装路径**已实测通过（桌面与开始菜单快捷方式均指向该路径）；
   - **含空格的路径**目前只验证了"运行"（把装好的整套放在 `含 空格 路径\`
     下启动，全流程正常），**"安装到含空格的路径"尚未验证**：安装器的
     静默模式在首个空格处截断了自定义路径（实测装到了 `安装 测试` 的前半段），
     交互式向导未测。若你需要装到含空格目录，请用交互式向导并自行确认装到
     了预期位置。
2. 覆盖安装即可升级，无需先卸载；用户数据自动保留。
3. 免安装版：`直播控制系统 1.1.0.exe`，双击即用。
4. 安装包未做代码签名，Windows SmartScreen 可能提示"未知发布者"，
   请核对 `SHA256SUMS-rc5.txt` 后再运行。

## 回退到旧版本（重要）

- **旧版本（1.0.0）读的是"进程工作目录"里的相对路径 `bili_areas_full.json`，
  不是数据目录**：它的 `AreaLoader` 直接用相对文件名，且启动后端时**没有设置
  工作目录**——所以实际读的位置随启动方式变化（用快捷方式启动时通常就是安装
  目录；从别的目录双击或命令行启动时就是那个目录）。它的**任务库
  （`live_tasks.db`）、状态、cookies、Excel 也都在同一个工作目录**，
  而不是 `%APPDATA%\bilibili-live-manager\data\`。
- 回退步骤：
  1. **先保留** `%APPDATA%\bilibili-live-manager\data\` 里最新的分区缓存与任务库
     （连同最新任务进度）。这是唯一"最新"的一份。
  2. **核对目标版本实际读哪里**再安置：先确认你打算怎么启动 1.0.0（快捷方式的
     工作目录、还是从某个目录双击），把选定的分区表与任务库放到**那个目录**里。
     不要假设"旧版本会自动继续读数据目录"——它不会。
  3. 1.0.0 的打包配置把 `*.json` 排除在 `backend/` 之外，所以**不要指望旧安装
     目录里一定留着一份分区表**；放之前先实际看一眼那个目录里到底有没有、
     是哪一份。
  4. 多个实例共用同一个旧发布目录时，**先核对各实例的数据差异**（任务库、
     分区缓存），再明确选择要用哪一份，不要用一个实例的数据静默覆盖其它实例。
  5. 1.1.0 升级时生成的 `migration_backup\<时间戳>\` 是**历史快照**，恢复它
     不等于恢复最新状态；**不要用任何较早的备份覆盖最新的任务进度**。
- 只要不拿旧备份覆盖最新数据，"回退"本身不会丢任务进度；但**跨版本回退后
  首次启动请先核对任务列表与完成天数**再继续使用。

## 已知限制

- 重复打开应用时，正在运行的实例会正常回到前台，但新起的进程会停在
  一个“端口被占用”的提示框上，点掉后自行退出（不影响正在运行的实例，
  也不会重复启动后端）。该现象在本版之前的构建中同样存在。
- 从未联网刷新过分区的用户会一直使用安装时自带的分区清单。
- 真实直播开播/停播/恢复需要真实账号与推流环境，未在本次验收中执行。
